# Architecture Decision Record 0008

## Title

Local Execution, Delegated Authorization, and No Application RBAC or Approval Service

---

## Status

Accepted

---

## Date

2026-08-18

This decision narrows the generic authentication methods described in ADR-0002: Microsoft Graph operations in the local HILOP product use delegated access. App-only support may remain for explicitly supported non-Graph providers or compatibility paths, but it is not an alternative HILOP authorization model.

---

# Context

HILOP is installed and run locally on a technician's workstation. It operates under the technician's user context and communicates directly with configured providers. It is not a server, shared web application, or network-aware coordination service.

Microsoft Entra ID and Active Directory already provide the authorization boundary for the systems HILOP administers. Microsoft Graph operations use delegated access, and AD operations use the technician's effective directory permissions.

Application-level RBAC would duplicate these established controls and could misleadingly imply that HILOP can grant authority that the underlying systems have not granted. A routed approval workflow would require shared persistent state, approver discovery, request delivery, and network coordination that do not exist in the local application model.

---

# Decision

HILOP will not implement application-level role-based access control (RBAC).

HILOP will rely on the authorization controls of each managed system:

* Microsoft Graph operations use delegated access and execute within the signed-in technician's Entra ID permissions and tenant policies.
* Active Directory operations execute within the technician's effective AD permissions.
* Other providers enforce the credentials and permissions presented to them.

HILOP will not implement centralized, multi-user, or routed approval workflows. It may require a local confirmation from the current operator before executing destructive or high-impact operations. Such a confirmation is a safety prompt, not an authorization grant or approval workflow.

HILOP will not gain a server, peer-to-peer, or other network coordination layer solely to support RBAC or approvals. Any future proposal to turn HILOP into a shared service requires a new product decision and architecture decision record; it is not an extension of the current desktop design.

---

# Consequences

Positive outcomes include:

* One authoritative permission model for each managed system.
* No duplicate role administration inside HILOP.
* No false impression that a local application role can override Entra ID or AD.
* No server infrastructure or shared approval-state dependency.
* A deployment model aligned with a technician-operated workstation tool.

Trade-offs include:

* HILOP cannot route an operation to another user for approval.
* HILOP cannot coordinate authorization state between separate local instances.
* Organizations that require separation of duties must implement it through Entra ID, AD delegation, PIM, Conditional Access, provider permissions, and their existing operational processes.

These trade-offs are intentional and define the product boundary.

---

# Alternatives Considered

## Application-Level RBAC

Rejected because it duplicates Entra ID and AD authorization, cannot elevate the underlying provider permissions, and adds a second role model that could conflict with the authoritative systems.

## Central Approval Service

Rejected because approval routing requires a network service, shared persistence, user discovery, and service operations that are incompatible with the local-workstation deployment model.

## Peer-to-Peer Approval Between Workstations

Rejected because it still introduces network discovery, trust, availability, security, and state-coordination requirements while effectively turning local instances into a distributed service.

---

# Outcome

HILOP remains a local technician console. The signed-in technician's permissions in Entra ID, Active Directory, and each provider determine what HILOP can do. HILOP may confirm an action locally, but it does not grant roles, approve authority, or coordinate approvals across users or machines.
